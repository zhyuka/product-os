# Changelog

Each version here matches `version` in `.claude-plugin/plugin.json`, the marketplace entry in `.claude-plugin/marketplace.json`, and `pyproject.toml`. Claude Code installs an update only when that number changes.

## Unreleased

- `ledger` reads a request as done when its session logged a Figma or FigJam edit on its words before your next request, in the JSON file `ledger.figma_edits` names. The edit is dated by the tool call that wrote the row, not by its hand-typed `at`, and a row whose `by` names the desktop session counts for the CLI ids that session ran under before. Unset, nothing changes. `is_correction(entry)` says whether your own words push back on work done, as `standing_of` counts them.
- `card_check` flags `your work?`, a question that puts a task to you instead of a decision ("will you label...", or a recommended "I'll review them") without saying why only you can, and `your words?`, a question sharing 3 or more words with an answer you typed on a card in the last 24 hours. Words inside a link no longer count toward any overlap, and the record lookup's limit is 300 s, up from 150, which a 4-question card's lookup passed.
- `recall.notes_files` names single files to search as notes, by path or glob, reading a file with the same bytes as one already taken once. `recall.memory_globs` replaces the memory source's list, for a setup whose memory cards are history.

- `figma_client mirror sync` refuses a file that `figma.mirror` doesn't name. Before, a sync of such a file, given with `--key`, wrote an empty page list into that file's outline. A second client sharing the state folder would read that outline as current until the next edit, with none of its pages mirrored. The self-test plants another client's mirror of an unnamed file and checks that a sync leaves it byte-identical; with the guard broken (`--break sync-any-key`), the sync rewrites its outline.
- `workspace_audit` gets four settings and a saved index. `index_roots` lets the cites index walk a folder that `skip` leaves out, such as a checkout kept inside one, and `generated_paths` names paths inside a build a skill generates. `map_places` resolves a map entry under a folder named by the word before it, such as a synced copy. `managed_hooks_only` makes a registered user hook a config miss where policy voids them all. The cites check now saves its file-name index after each walk. Commit mode reads it while it's under a day old, and walks again only when a cite misses it. Before, each commit that staged a doc walked the whole root, and on a slow disk that walk can take a minute or more. "disagreed on whether" joins the phrases that cite a file to say it's gone.
- `tokens.keychain` in your own `~/.claude/product-os.json` names the keychain item a token is also read from, such as `{"service": "env/{name}", "account": "{user}"}`. Before, a token was read only from the environment or from the `product-os` item, so a keychain that kept it under another name gave "did not run" in any process that hadn't loaded it: a scheduled job, a hook, a GUI app. `kit_config.token()` tries the `product-os` item first, then this item for each name it was asked for. `figma_auth` reads the same items. Each value stays in memory for the run, and none is printed or written. A project's file can't set it: its value is left out and named, because it would choose which of your secrets a tool reads.
- `triage.ledger_file` says where the ledger file is: a path from the project folder, or `false` for a project that keeps none, and `triage_lists`, `open-question` and `triage` all read it. Before, `triage_lists` read only `.claude/open-questions.md`, so a project that keeps its open questions elsewhere got "Ledger file: did not run" on every run. The other path `open-question` allowed, one named in the project's `CLAUDE.md`, was one the tool never read. With `false`, its line says the project keeps none, and it exits 0. A missing file at the path still didn't run.
- `figma-writes`: each row or decision block on a board reads alone, heard once with no pre-read. Every line says what it is about, gives a number rather than an adjective, and spells out its terms, and a recommendation gives the fact that decides it. Lines like "− tagging work first" and a reason ending "we'll need all of them" left a room with no pre-read unable to tell what they meant.
- `setup-kit`'s setup check counts the project's listed checks only when each is accepted on this machine as it is now, since the push check runs no other. Before, it passed with any check listed, so it never gave `product-os accept`. In the v0.1.4 live evals, 2 of 3 runs with the plugin left that line out.
- `build-change` reports each verdict as its checker's, such as "the reviewer said MATCHES at 1440", and ends with what the person decides: the section waits for their approval. In the live evals, a report that said the build "matches the mockup" read as a sign-off. With the plugin, 2 of 3 v0.1.4 runs read that way, and none without it.
- `retro` opens by saying the run has already started and not to call the Skill tool for retro. Claude Code expands `/product-os:retro` before Claude's first turn, then refuses a Skill call for a skill only a person may start, and that refusal says to ask the person to type the command. In the v0.1.4 live evals, one `retro-quiet` run made that call, asked for the command and wrote no report. Its description now says to schedule it with a task that reads and follows its SKILL.md: a `/loop` or cron run passes `/product-os:retro` on as plain text, since only a person may start retro.
- The trigger tests in `evals/triggers.py` no longer count a Skill call that Claude Code refused as the skill firing. They name a skill only a person may start as not run, rather than test it. `retro`'s one trigger query, "Run the retro", could pass only through the refused call that ended a v0.1.4 `retro-quiet` run, so it is gone.
- The live evals' Ubuntu job runs on Ubuntu 24.04. In v0.1.4 the probe wrote neither file in either arm on `ubuntu-latest`, which has been moving to Ubuntu 26.
- A probe tag such as `v0.1.4-probe.1` runs only the Ubuntu probe, for up to $0.25, and `release.yml` runs only on a release tag such as `v0.1.4`.

## 0.1.4

- The Linux live evals use the default temp folder again. With `TMPDIR` at `/ev`, Bash in the v0.1.3 Linux evals ran no command at all, in either arm. Each call ended with `.bashrc: Permission denied` and a seccomp error about nested user namespaces. With the default, Bash runs and only its writes fail, as in v0.1.2.
- macOS runs every live eval case now, capped at $8.25, and Ubuntu runs only a new probe case, `sandbox-write`, capped at $0.25. The total per tag stays at $10. On Linux, `claude plugin eval` denies sandboxed writes under the temp folder that holds its runs ([anthropics/claude-code#104631](https://github.com/anthropics/claude-code/issues/104631)). So the v0.1.2 and v0.1.3 Linux scores measured the sandbox, and the plugin lost to the bare arm on skill cases. On macOS the runs' folder is exempt, and shell writes worked in every run of both releases. The probe writes a file in the run's folder and one through a `mktemp` folder. Ubuntu tries it with `TMPDIR` at `~/.cache/claude-eval-tmp`, which fixed writes on two Linux hosts in that issue, and with Ubuntu's user-namespace limit lifted.
- The SessionStart hook tells Claude which folder is the project and which is the plugin's, every time. Claude Code names the plugin's folder above each skill it loads. In the live evals, runs with the plugin looked for the project's files there or ran `cd` into it before the launcher. The hook names neither folder when one holds the other, as when you work on the plugin itself.
- The live evals' step summary counts the runs with the plugin that took the plugin's folder for the project, by a `cd` into it or a path there outside the plugin's own files. Each such run is named under its case with its first such call.
- `figma-writes` puts the answer first in each part of a board section, with its evidence beside it, and a long set in its own table or picture. Each open decision is one block: the question, its options as nested bullets, then the recommendation and its reason. Its reference adds the board-text rules: cells as short fragments, numbers the room compares on one shared scale, and status as a word as well as a colour.
- `figma-writes` folds a board section into the fewest parts that show how its items relate, often one table with a row per item and its relations as columns, and keeps the evidence in its own zone. Each option in a decision block now carries what it gains and what it costs, and a section opens with the page or product it serves and the nearby ones it doesn't cover. A spec for Design gives the data and what's agreed, and leaves layout and behaviour to Design.

## 0.1.3

- Each skill line that tells the agent to run the launcher now names it by its path in the plugin, `"${CLAUDE_PLUGIN_ROOT}/bin/product-os"`. It runs in the session's working folder with no `cd` first. In the v0.1.2 live evals on Linux, Bash had no `product-os` on its PATH. Skills that read their settings through `kit_config` then worked without them. Where another agent tool leaves the path unfilled, a skill takes the plugin folder from its own path, and falls back to plain `product-os` only when no launcher is there. Lines the person runs in their own shell still say plain `product-os`. `doctor` also flags a skill that calls a missing tool through the launcher's path.
- `miss-to-check` no longer stops to ask about a leftover defect before it gives the check's entry. It carries on and puts the whole entry in its report. In a v0.1.2 live run, it found the leftover, then stopped without the entry.
- The Linux live evals give `claude plugin eval` a temp folder outside `/tmp`, at `/ev`. Each run's folder is made there, and on Linux the eval's sandbox denies writes anywhere in `/tmp`. So Bash could write nothing, and cases that write through the shell failed with "Read-only file system". The name stays short because Claude Code moves Bash's own temp folder back to `/tmp` when its path passes 44 bytes. The setup step fails before any case runs if it would.
- `figma-writes` says what a board section is for: the team works from it live in the room. Each part takes the form its use needs, such as a table for a lookup, stickies for a set the room will sort, or shapes and arrows for a flow. A small picture goes beside a part the room should get at a glance. A section carries the answers the work proposes and the evidence for each. That's every option, value and item a point rests on, with data measured on the real population or taken from published research. Before, the skill said to match a teammate's section on the same board and add nothing it lacked.
- The unit tests run in parallel through `.github/run_tests.py`, one process per CPU, up to eight. On your own machine it also skips a test that passed before, while nothing it read has changed. CI runs every test. The long page loops in the browser tests are one test per page now, so a failure names its page. On an 18-core Mac the full suite went from about 23 minutes to under 4.

## 0.1.2

- The live evals' step summary now says what each failed run did. It lists each tool call with the start of its result or why it was denied, then the end of the last reply. A judge records only its votes, so before this the summary couldn't say why a run failed. `evals/live.py` keeps each run's trace for it. Token-shaped strings are masked, and the traces aren't uploaded.
- On Windows, a live eval job where no run signed in now passes with a notice that says why. Claude Code turns off its shared federation token cache there. So each process presents the same single-use GitHub token, and only the first is accepted. On Ubuntu and macOS the same outcome still fails the job, since there it means the federation rule is wrong.
- `review` makes the reviewer's temp folder with `mktemp -d "${TMPDIR:-/tmp}/review.XXXXXX"`. A bare `mktemp -d` on macOS ignores `TMPDIR` and writes under `/var/folders`, which Claude Code's sandbox refuses. In a sandboxed session there, the diff file was never written.

## 0.1.1

- `reconcile` has a runner for its open-items sweep, `skills/reconcile/scripts/open_items.py`. It runs each source in the project's `rebase.surfaces` list with a 5-minute cap, prints ran or DID NOT RUN for each, the count and the top items, then the total, listed, skipped and uncovered. `--surfaces FILE` reads the list from a file instead.
- The design check finds the Figma client only in the plugin's own `tools/` folder, and no longer reads `FIGMA_CLIENT_DIR`. The client uses that variable for its state folder, so setting it for one meaning broke the other.
- A tool run through a symlink imports the modules beside its real file, and a tool imported by another no longer puts its own folder ahead of the importer's imports.
- On Windows, a linked tool imports its own siblings too. Python leaves the link's folder first on `sys.path` there, so each tool that imports a sibling puts its own folder in that place when it runs. The open-items runner runs each source in Git Bash, found the way Claude Code finds it for a hook command (`CLAUDE_CODE_GIT_BASH_PATH` first); with no Git Bash, each source is DID NOT RUN and says what to set. Its `wrap` finds a `.cmd` tool, such as `az`, with PATHEXT.
- On Windows, the tools' self-tests keep out of your own `~/.claude`. Python reads the home folder from `USERPROFILE` there and ignores `HOME`. Each self-test that plants an empty home now sets both. Before, `kit_config --selftest` wrote its planted settings over your `~/.claude/product-os.json` and added planted entries to your accepted-commands file. The open-items self-test never found the list it planted.
- doclint can lint AGENTS.md and a skill's own files, for a setup whose skills and agent notes are written for people to read. `doclint.lint_names` lists built-in exempt names to lint anyway, such as `["AGENTS.md"]`, and `doclint.exempt_skill_files: false` lints `skills/<name>/<file>.md` outside a plugin. A plugin's `skills/` folder stays exempt. Unset, nothing changes.
- The README now opens with what Product OS adds: checks an agent can't pass for itself. It credits Anthropic's AI-native SDLC playbook for the six stages and the files between them, instead of saying the plugin follows it.
- `build-from-design`'s design check tells which icon is drawn. It reads the frames with Figma's shape paths (`geometry=paths`), draws each icon's paths and the build's SVG in the page's browser, and compares them to 1/64 px, so an unturned chevron-down in chevron-up's place, or another icon of the same size, is a miss. An icon whose paths are missing is DID NOT RUN, and the check exits 2. Frames cached before this are read again.
- On a Windows git clone, the ado skill loaded with no name or description, and `claude plugin validate` failed on it. Git for Windows checks text out with CRLF, and with CRLF Claude Code can't read an unquoted description that holds `: `. `.gitattributes` now checks every text file out with LF, and the description is quoted. `tests/test_frontmatter.py` and a Windows run of `claude plugin validate` in `tests.yml` catch it on every push.
- figma_post refuses a comment that asks design something your record already settles, on the files you list in `figma.settled_files` (its eighteenth rule). It runs on `new`, `reply`, a batch `edit` and `figma_attach.py edit`. `--asks <id>` (batch: `"asks"`) names the record entry an ask is about. Your own command in `figma.settled_cmd` says what the record holds: it reads one JSON request on stdin and prints each reason, and a listed file with no command refuses every ask. drafts_store runs the same rule on drafts still in the drafts file (rule `ask`, or `ask not run`, which exits 2, when the command couldn't judge a draft), and card_check counts both. Unset, nothing changes.
- When the reviewer hook blocks a write, its reason tells the reviewer not to try another way, and to name each problem and its fix in its answer. In the v0.1.0 live evals, a reviewer whose `sed` or redirect was blocked sometimes ended without naming the typo it was asked to review.
- `go` reads the project's own routes before it picks a row. Its first tool call is now `product-os kit_config`, in the session's working folder, unless the request names a skill. In the v0.1.0 live evals, `go` sent a design link to `build-change` without reading the route that sends it to the project's own page skill.
- A command setting that isn't accepted now says whose step the accept is. `product-os kit_config` and every tool that reads a setting through it print the accept line as `product-os kit_config accept <key>`, then say an agent runs neither that line nor the command and reports that part as NOT RUN. Before, the line read "The person reads it there and runs: python kit_config.py accept <key>", and in a live run of `check-page`, the agent ran that line itself in 2 of 3 runs. `check-page` says the same.
- Run from inside the plugin's own folder, a tool's refusal now says where to run it: in the folder the session works in, with no `cd` first. `kit_config`'s also says not to read the project's `.claude/product-os.json` in its place. Before, through the `product-os` command on macOS, the line said only "--project <your project folder>", because `/bin/sh` drops the folder you came from. In a live run, 10 of 13 sessions changed into the plugin's folder at some point, and one then ran a build command from the project's file that wasn't accepted. `check-page` now says to run `product-os kit_config` in the session's working folder.
- `build-from-design`'s report lists what it changed under "Changed:", not "Done:". The same skill says a section with a missing frame isn't done. In a live run, each of 3 reports named the missing phone frame first and still failed the grader that wants the section not called done.

## 0.1.0

The first release.

- One plugin, Product OS: install `product-os@product-os`. The command is `product-os`, for the checks (`product-os check`, `prove`, `accept`, `gates`, `design`, `demo`) and for the tools (`product-os <tool>`). The Python module is `product_os`.
- A project's values live in `.claude/product-os.json` and its checks in `.claude/product-os-checks.json`. The checks also write `.claude/product-os-checks-proofs.json` and, beside your own config, `product-os-checks.json` and `product-os-checks-accepted.json`. `PRODUCT_OS_CONFIG`, `PRODUCT_OS_PYTHON` and `PRODUCT_OS_NO_KEYCHAIN` set where they're read and how. Tokens come from the keychain service `product-os` or the environment, data from `~/.local/share/product-os` and `~/.local/state/product-os`, and caches from `~/.cache/product-os`.
- The settings the build and review skills read share one group, `app` (`dir`, `widths`, `build_cmd`, `serve_cmd`, `check_cmd` and more). The push check reads the same keys. Every key is in `docs/config.md`.
- A project's `.claude/product-os.json` can't choose what runs on your machine. A setting that runs a command (a key ending in `_cmd`, and the few `docs/config.md` lists) counts from the project's file only once you accept it with `product-os kit_config accept <key>`, and again after it changes.
- The skills follow the six stages of the AI-native SDLC playbook, each leaving a file the next one reads: `intent`, `spec`, `templates/plan.md` for plan mode, `build-change`, `build-from-design`, `review-change`, `deliver-change`, `go` and `retro`, with `check-page` for QA and `setup-kit` for setup.
  - `review` writes the change to a diff file and gives the reviewer the spec, the project's `REVIEW.md` (template in `templates/`) and that file.
  - `reconcile`, `open-question` and `triage` file each question only on its own yes and read every tracker write back. `reconcile` makes the archive moves and local fixes itself and asks only for deletes and outward steps.
  - `triage` shows up to four decisions a card, each its own question with its full record, and only from lists that ran. `triage_lists` prints which lists ran, quoting each refusal, and ends with a line saying to paste them first; the card's reply opens with its lines. The `challenger` agent runs once before a card, and only settings, hooks, gates and one-way steps wait on it.
- Hooks for Claude Code. An agent your config names as a reviewer can't write files, shell writes included. A builder can't stop until its QA command passes after its last edit, and a QA run piped into another command or ended with `|| true` doesn't count. The line at session start says what the hooks will block.
- The reviewer agent can only read, search and list files. page-qa has no file-writing tool, and check-page builds the page before starting it, then fails the run if page-qa changed the build, the git folder, the project or the accepted files (`product-os qa_snapshot`).
- `product-os check` runs a project's own checks from a skill, a git hook or CI. `product-os prove` records that each check failed a planted bad case and passed a good one, and a check without that record doesn't count. A project can add checks but can't remove one or change its cases.
  - A check's proof covers every file in a folder its command names, and the baseline in `design/` when a design command reads it by default.
  - On your own machine a project's check runs only once you accept it. `product-os accept` prints each check's command, proves it, and keeps the proof in `product-os-checks-accepted.json` beside your own config. Run it once in each project. In Claude Code, the hooks ask you before an agent runs `accept`, passes `--run-listed` or edits the accepted file.
  - `check --run-listed` runs every listed check and counts the project's own records, for CI, which has no accepted checks. The CI templates pass it.
- `product-os design` records a Figma design as a baseline in the repo, lists each state its frames draw, drives a build into each one, and says when the design was edited after the baseline. `design exercise` waits for the animations inside a component's shadow root to end, as it does for the page's own, and stays on the build it was given: a click that opens another site passes and is reported, and the site isn't loaded in the page's own window. A link that opens a new window or tab isn't stopped yet.
- `product-os gates` measures what a design rarely draws, at each width its frames have: something clickable that Tab can't reach or leave, a control Tab reaches that `aria-hidden` hides from a screen reader, a menu only a hover opens, a button-like element that ignores Enter and Space, tabs or a list box only a click works, a Tab stop that doesn't show focus or shows it at less than 3:1 against what's beside it, an element that runs past the right edge, a blurry or broken image at 2x, and motion that keeps running with reduced motion asked for. Each failure names the element and the number.
- `build-from-design`'s design check compares every value exactly, at the precision the browser keeps: lengths to Chrome's 1/64 px step, type values to 0.001 px, colours to 8 bits. It checks text, lines, box edges, solid fills and icons, and its report names what it doesn't compare.
- The check, review, setup and miss-to-check skills treat what they read as data, which can't add a command, accept a check or change a result.
- CI templates for GitHub Actions and Azure Pipelines in `ci/`, installing `product-os` at `v0.1.0`. `ci/pre-push` runs the project's checks, build and check commands, refuses a DID NOT RUN line, and refuses when `product-os` isn't on PATH. `ci/pre-commit` refuses a commit that stages a key or a token. `/product-os:setup-kit` installs both.
- Tracker tools:
  - `ado_rest.py decisions --from <file>` lists the open decisions in a tracker cache someone hands over, and refuses one pulled more than 30 minutes ago or with no pull time. `triage` reads such a file only through it.
  - `ado_write.py delete <id>:<rev>` sends a Removed item to the recycle bin, after writing an undo file, and reads back that it's there; `restore <id>` brings it back. Before any write, `ado_write.py` prints the session's own earlier sentences that put off work on that item.
  - `ado_write.py field` and `batch` refuse a write that drops a line someone else first wrote in a title, description, acceptance criteria or repro steps, and print the merged value with their lines on top. `--replaces "<why>"` lifts it. `batch` also refuses a key it doesn't send, such as `"delete": true`, before anything goes out.
  - `ado_links` finds the work-item ids a doc leaves bare and links them. `ado_write.py` and `ado.py new` link each bare id they send, and `doclint` flags one in a doc when `ado.org` and `ado.project` are set.
- Figma tools: `figma_post` refuses a new thread that links an open comment of your own (fix it and edit that comment instead). `figma_comments` has a self-test.
- The tools that print work-item ids or Figma nodes (recall, digest, drafts_store, ado_rest, figma_post, scheduled_audits) end each line with their links.
- `session_close` checks the side sessions a session started. One that still owes something makes the session owe too.
- `upkeep` removes empty `~/.claude/session-env` folders older than 14 days that no running session owns.
- `recall` prints a record that a fork, a continuation or a resume copied once, under the session that wrote it first, and names the copies on "also in". It runs in its own process when the machine won't start a process pool, and says so. It reads a message the app queued behind its status reminders by the text after them.
- `scheduled_audits` shows each red audit's days and owner, notifies only on a new red or one unowned for 3 days, lists the reds with `--reds`, and lets an extra audit set its own timeout.
- Add three ask rules to your settings: `Bash(*ado_write* delete *)`, `Bash(*ado_write* restore *)` and `Bash(*figma_attach* resolve *)`. `ask_rules.py` fails until they're there.
- A tool never takes a folder inside the plugin's own folder for the project, unless it has a `.claude` folder of its own, as the shipped example does. Run there, the tool refuses in one line, exit 2, naming the `--project` to run it again with; `$CLAUDE_PROJECT_DIR` is taken as given. This covers `kit_config` and the tools that read settings through it, `triage_lists`, `skill_lint`, `cc_logs`, `agent_gate_stale`, `ado_links`, and `product-os check`, `prove` and `accept`.
- The skills run their tools with `python3`, which every macOS and Linux machine has.
